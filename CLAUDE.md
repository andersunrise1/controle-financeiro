## Visão do produto

App de controle financeiro pessoal focado em **compras de mercado**. A ideia central do usuário:

- A pessoa vai ao mercado e, conforme coloca itens no carrinho, registra cada produto e seu preço — digitando manualmente **ou** tirando uma foto (do carrinho/nota fiscal) para o app extrair os itens automaticamente via IA.
- Com isso, o app sabe não só "quanto gastei no mercado", mas **quanto cada produto individual custou**, mês a mês.
- Dashboards interativos devem mostrar: quanto a pessoa gastou a mais/a menos em relação aos meses anteriores, e **quais produtos aumentaram de preço** ao longo do tempo.
- Ou seja, o diferencial real não é só "livro-caixa" (entradas x saídas), é rastreamento de **preço por produto ao longo do tempo**.

## Estado atual do código (MVP já implementado)

Monorepo simples, dois apps Next.js separados, sem workspace compartilhado:

```
Controle Financeiro/
├── backend/    → API Next.js (porta 3001) — rotas em app/api/
└── frontend/   → Next.js + React + Tailwind v4 (porta 3000)
```

**Backend** (`backend/`):
- `lib/db.ts` — SQLite via `better-sqlite3` (`data/finance.db`), duas tabelas: `users` (id, name, email, password_hash) e `transactions` (id, user_id, type: 'income'|'expense', amount, description, date).
- `lib/auth.ts` — JWT (`jsonwebtoken` + `bcryptjs`).
- `lib/cors.ts` — helper de CORS/response JSON compartilhado entre rotas.
- Rotas: `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`, `GET/POST/DELETE /api/transactions` (com `summary`: totalIncome, totalExpense, balance calculados no GET).

**Frontend** (`frontend/`):
- `lib/api.ts` — client HTTP para o backend; `lib/auth-context.tsx` — contexto de auth (token em localStorage).
- Páginas: `/`, `/login`, `/register`, `/dashboard` (protegida via `ProtectedRoute`).
- Componentes do dashboard: `BalanceCard` (saldo), `ClusteredChart` (gráfico de colunas entradas x saídas por mês), `TransactionForm` (form manual: tipo/valor/descrição/data), `TransactionList`.
- Visual: tema dark com botões 3D neon (verde para entrada, vermelho para saída) — já com identidade visual definida, não é genérico.

**O que existe hoje é só um "livro-caixa"**: transação genérica com `description` livre, sem conceito de produto/item, sem mercado/loja, sem histórico de preço por item, sem OCR/câmera, sem app mobile (só web responsivo via Next.js).

**Categorias com cores neon (2026-08-17)**: transações ganharam um campo `category` (7 categorias fixas: Salário, Mercado, Moradia, Transporte, Lazer, Saúde, Outros), cada uma com uma cor neon própria definida em `frontend/lib/categories.ts` (espelhado em `backend/lib/categories.ts` para validação). Migração leve em `db.ts` (`ALTER TABLE ... ADD COLUMN category DEFAULT 'Outros'` se a coluna não existir) — transações antigas viraram automaticamente "Outros". `TransactionForm` ganhou um `<select>` de categoria; `TransactionList` mostra uma badge colorida por categoria. O gráfico original (`ClusteredChart`, Entradas x Saídas) saiu do verde/vermelho pra azul claro/vermelho neon; um novo `CategoryChart` mostra gasto por categoria por mês — só renderiza `<Bar>` para categorias efetivamente usadas nos dados, então o número de cores no gráfico cresce organicamente conforme o usuário varia as categorias (era o pedido original: "não ficar só nesse gráfico vermelho e verde").

## Região / moeda — 16 países (2026-08-18)

O app deixou de ser só sobre "controle de compra de mercado" pra ser **controle financeiro + conversor de câmbio**, com foco em quem viaja entre países da América Latina:

- `frontend/lib/regions.ts` — 16 regiões (Brasil, EUA + Argentina, Paraguai, Uruguai, Chile, Venezuela, Colômbia, Peru, Bolívia, Equador, El Salvador, México, Porto Rico, Honduras, Guatemala), cada uma com moeda, locale ICU (formatação numérica correta por país) e idioma (PT pro Brasil, EN pros EUA, ES pros outros 14 — Equador/El Salvador/Porto Rico usam Dólar de verdade, dolarização real, não erro).
- `backend/app/api/exchange-rates` + `frontend/lib/exchangeRates.ts` — cotação de câmbio **ao vivo**, buscada de uma API gratuita (open.er-api.com, sem chave), com cache de 12h (backend em memória, frontend em localStorage). Se a API cair, cai pra uma tabela fixa em `regions.ts` (`REGION_EXCHANGE_FROM_BRL`) como último recurso.
- `frontend/components/CurrencyConverter.tsx` — conversor independente (De/Para, qualquer um dos 16 países), pensado especificamente pro caso de uso "casal viajando de motorhome pela fronteira" que o usuário descreveu.
- `frontend/components/LanguageSwitcher.tsx` / `RegionSelect.tsx` — seletor de país/moeda (dropdown customizado com bandeiras em SVG próprio — `FlagIcon.tsx` — não emoji, porque o Windows não renderiza emoji de bandeira como imagem, só mostra o código do país em texto).

Motivada por uma pergunta direta do usuário: por que o app parava de funcionar no celular sempre que ele fechava o notebook? ## Modo claro/escuro (2026-08-22, web, a pedido do usuário)

Pedido junto com o botão de editar, na mesma mensagem. `app/globals.css` ganhou um sistema de variáveis CSS (`--bg-dark`, `--bg-card`, `--text-primary`, `--border-color`, etc.) com um bloco `:root` (valores escuros, os originais) e um `[data-theme="light"]` que sobrescreve só as cores estruturais/de chrome — fundo, cards, texto, bordas. As cores de marca (verde/vermelho neon, gradiente pôr do sol, cores de categoria) ficam **iguais nos dois temas**, de propósito: são identidade, não chrome, e o efeito neon depende de um fundo escuro pra parecer neon. `lib/theme-context.tsx` (`ThemeProvider`/`useTheme`, mesmo padrão de `auth-context.tsx`/`i18n-context.tsx`) guarda a escolha (`"dark"`/`"light"`) no `localStorage` e escreve `data-theme` no `<html>`; `ThemeToggle.tsx` (ícone sol/lua) foi adicionado na `Navbar`, ao lado do seletor de idioma.

**Dois bugs reais achados na verificação ao vivo, não só escritos por cima:**

1. **Cache do Turbopack preso, servindo CSS de antes da sessão continuar** — depois de editar `globals.css`, o `data-theme="light"` nunca aparecia no CSS compilado servido pelo navegador (`fetch` direto no chunk confirmou: nem o seletor `[data-theme="light"]` nem a cor `#faf7f2` apareciam em lugar nenhum, mesmo com o servidor reiniciado do zero). Causa: a pasta `.next` tinha cache de uma versão anterior do arquivo (de antes dessa conversa continuar de um resumo) que sobreviveu a um `npm run dev` normal. Resolvido apagando `frontend/.next` inteiro e subindo o servidor de novo — só então o CSS novo apareceu no bundle servido.

2. **Verde/vermelho neon puro é ilegível no tema claro** — contraste calculado de verdade (fórmula de luminância relativa do WCAG, não só olhômetro): `#39ff14` (verde neon) contra o novo fundo claro `#faf7f2` dá **1.27:1** — bem abaixo do mínimo de 3:1 pra texto grande, e é exatamente a cor do saldo/valores nas telas mais importantes do app (`BalanceCard`, `TransactionList`). Corrigido criando `--text-accent-green`/`--text-accent-red` (e o par de alerta `--alert-success-text`/`--alert-error-text`/`--alert-warning-text`, e `--text-accent-cyan` pro indicador de região ativa) com valores diferentes por tema: no escuro, ficam iguais às cores neon originais (nenhuma mudança visual pra quem sempre usou o app no escuro); no claro, usam tons bem mais escuros da mesma cor (`#1a7a0e`/`#c81e3a`) que passam 5:1+ de contraste. ## Modo claro/escuro (2026-08-22, mobile)

Mesmo recurso do web (2026-08-22), portado — a parte mais trabalhosa desse dia, por uma razão estrutural do React Native que o web não tem: `StyleSheet.create({...})` normalmente roda uma vez, no carregamento do módulo, fora de qualquer componente — então nenhum estilo definido assim pode reagir a um tema que muda em tempo de execução. `mobile/src/theme.js` virou `getColors(scheme)` (um objeto `DARK`/`LIGHT`, mesmos valores hex do `globals.css` do web) em vez do antigo `colors` fixo; `mobile/src/context/ThemeContext.jsx` (mesmo padrão do `LocaleContext.jsx` existente, trocando `localStorage` por `AsyncStorage`) expõe `{theme, colors, toggleTheme}`. Todo componente/tela que usava `import { colors } from "../theme"` (25 arquivos) passou a chamar `useTheme()` e envolver seu próprio `const styles = StyleSheet.create({...})` num `function getStyles(colors) { return StyleSheet.create({...}); }`, chamado a cada render com as cores atuais — funciona porque `StyleSheet.create` é seguro de chamar repetidamente (só registra os estilos de novo), só um pouco menos otimizado que a forma tradicional, aceitável na escala desse app.

Mesma separação de tokens do web: cores estruturais (fundo, cards, texto, bordas) mudam por tema; cores de marca (verde/vermelho neon, gradiente pôr do sol) ficam fixas nos dois temas — usadas em botões/badges/pontos decorativos autocontidos (o toggle Entrada/Saída, o checkbox de recorrência marcado, os pontos de legenda dos gráficos). Onde a cor neon aparecia como **texto** direto sobre o fundo da tela (saldo, valores +/-, links "Cadastre-se"/"Entrar", o texto do resultado no conversor de moedas) — o mesmo problema de contraste do web (`#39ff14` só bate ~1.3:1 contra o fundo claro nada perto do mínimo de 3:1) — usa os novos `accentGreenText`/`accentRedText` (idênticos ao neon no escuro, uma versão bem mais escura no claro). Mesmo padrão pra `accentCyanText` (região ativa no seletor) e `warningText` (aviso de câmbio volátil no conversor). `Alert.jsx` tinha exatamente o mesmo bug que o `Alert.tsx` do web precisou corrigir no mesmo dia — texto `#ff6b85`/`#7cff5c` fixo sobre um fundo tintado a 10%, ilegível no tema claro — corrigido com o mesmo `accentRedText`/`accentGreenText`.

Um bug real, achado só nesse arquivo, sem equivalente no web: `TopNavBar.jsx`'s botão de logout tinha `backgroundColor: colors.bgCardHover` (que vira um creme claro no tema claro) com `color: "#ffffff"` fixo no texto — texto branco sobre fundo claro, seria invisível assim que o modo claro existisse. Corrigido pra `colors.textPrimary` (que já é escuro no tema claro, claro no escuro). `ThemeToggle` (sol/lua) foi adicionado no `TopNavBar`, ao lado do `RegionPicker`, mesmo lugar do `ThemeToggle` no `Navbar.tsx` do web. `AppNavigator.jsx` também passou a alimentar o próprio `theme`/`colors` do React Navigation (`NavigationContainer`'s prop `theme`) — sem isso, as transições de tela usariam as cores padrão da biblioteca (branco/preto) em vez da paleta do app, um flash visual real durante a navegação.

Verificado ao vivo na preview mobile-web: registrei uma conta de teste, cliquei o toggle e confirmei visualmente e por screenshot que fundo/cards/texto mudam de fato (não só um atributo settado sem efeito, o mesmo tipo de bug real que o web bateu nesse mesmo dia por causa de um cache do Turbopack preso — aqui não aconteceu, testado do zero); criei uma Saída de R$55 e confirmei o saldo e o valor renderizando num vermelho escuro legível (não o neon lavado) no tema claro; testei o botão de editar no tema claro — mesmo comportamento correto de antes; testei Mercado e Feedback no tema claro — tudo legível; recarreguei a página inteira e confirmei que o tema persistiu (`AsyncStorage`, não só estado React); voltei pro tema escuro e confirmei visualmente que nada mudou do visual original do app (mesmo verde/vermelho neon puro, mesmo fundo escuro).

## Redesenho da aba Mercado — filtro Ano/Mês, cor fixa por produto, quantidade (2026-08-23, web, a pedido do usuário)

Pedido do usuário: o gráfico original de Mercado ("Produtos que você mais compra") era um ranking de frequência **de todos os tempos**, sem noção de mês/ano — não dava pra responder "comprei mais arroz em julho ou em agosto" nem "quanto gastei no mercado esse mês". Redesenhado em torno de um filtro Ano+Mês compartilhado por dois gráficos e o histórico.

**Backend**: `transactions` ganhou `quantity` (REAL, nullable) e `unit` (TEXT, nullable) — mesmo padrão de migração preguiçosa já usado pra `category`/`recurring_id` (checa se a coluna existe, `ALTER TABLE` se não). `lib/categories.ts` ganhou `UNITS = ["kg", "g", "L", "ml", "un"]` + `isValidUnit`. `POST`/`PUT /api/transactions` aceitam `quantity`/`unit` opcionais, validando quantidade > 0 quando presente (mesmo padrão do `amount`) e a unidade contra a lista fixa.

**Filtro Ano/Mês** (`components/MercadoFilter.tsx`, `lib/mercadoGrouping.ts`): dois `<select>` — Ano (só anos com compra real, mais recente primeiro) e Mês ("Ano inteiro" ou um mês específico). O ano padrão é o mais recente **com dados de verdade**, não necessariamente o ano civil atual (uma conta nova sem nenhuma compra ainda usa o ano atual como fallback). `filterMercadoByScope(transactions, year, month)` centraliza a lógica de filtro — usada pra restringir tanto o gráfico de Produtos quanto o Histórico ao mesmo escopo, então trocar o mês filtra os dois juntos, exatamente como pedido ("digitar julho, aparece tudo que comprou em julho").

**Dois gráficos, não um só** (decisão de design explicada e confirmada com o usuário antes de implementar, pra evitar um gráfico de 30 cores × 12 meses simultâneos ilegível):
- `components/MercadoMonthlyChart.tsx` ("Gasto Total por Mês") — sempre os 12 meses do ano selecionado (mesmo os com R$0, pra não parecer que o ano é mais curto do que é), independente do filtro de mês — dá a visão geral de tendência, no mesmo estilo do "Entradas vs Saídas por Mês" que o usuário pediu como referência.
- `components/MercadoChart.tsx` (agora "Produtos", não mais "Produtos que você mais compra") — respeita o filtro: com "Ano inteiro" agrega o ano inteiro (responde "o que comprei mais em 2026"); com um mês específico, só aquele mês (responde "gastei mais em arroz em julho ou agosto", trocando o filtro e comparando as duas leituras). Métrica mudou de **contagem de compras** pra **R$ total gasto** — é a única unidade comparável entre produtos diferentes (kg de arroz vs L de leite vs unidades de ovo não dá pra somar num eixo só, R$ dá).

**Paleta de cores por produto** (`lib/productColors.ts`): 30 cores categóricas fixas (não mais o degradê pôr do sol compartilhado) — uma função de hash determinística no nome normalizado (trim + lowercase, mesma normalização que já agrupava "Leite"/"leite") escolhe sempre a mesma cor pro mesmo produto, em qualquer mês, sem precisar guardar isso no banco. Implementado com `<Cell>` do Recharts (uma cor por barra) — **achado real durante a verificação**: o bug antigo documentado nesse arquivo (barras do Recharts não renderizavam nesse ambiente de teste) não se repetiu dessa vez, nem com `<Cell>`; aparenta ter sido mesmo uma limitação pontual do ambiente de navegador automatizado daquela sessão, não do `<Cell>` em si — confirmado ao vivo com screenshot real mostrando cada produto com sua cor (roxo pro "arroz", rosa pro "Feijao", etc.).

**Quantidade + unidade**: `MercadoQuickAdd.tsx` ganhou dois campos novos (Quantidade + um `<select>` de Unidade) ao lado do Preço, ambos opcionais — quem não quer se preocupar com isso continua registrando só produto+preço como antes. `TransactionList.tsx` mostra a quantidade/unidade no histórico quando presente (ex: "Arroz · 5 kg"). O modo de edição já existente (Dia 22) ganhou o pré-preenchimento desses dois campos automaticamente, sem código novo de sincronização.

Verificado ao vivo, ponta a ponta: registrei "Arroz" (R$25,90, 5 kg) em agosto/2026, depois duas compras de julho/2026 direto no banco ("Feijao" R$12,50 2kg, "arroz" minúsculo R$30,00 6kg — pra testar a normalização de case) — confirmei que "Ano inteiro" agrupa "Arroz"/"arroz" como um produto só (30+55,90 ≈ R$55,90 numa barra roxa só), que trocar pra "Julho" filtra o gráfico de Produtos E o histórico pros 2 itens de julho (some a compra de agosto dos dois), que o gráfico "Gasto Total por Mês" continua mostrando os 12 meses independente do filtro de mês, e que editar uma compra pré-preenche quantidade/unidade corretos. Testado nos dois temas (claro/escuro) — cores dos produtos, textos e dropdowns legíveis nos dois. `npx tsc --noEmit` limpo (só o erro pré-existente e não relacionado do `CategoryChart.tsx`); `npm run lint` nos mesmos 7 erros já documentados de `set-state-in-effect` (nenhum novo — `mercado/page.tsx` já estava na lista, só manteve o mesmo padrão de `useEffect` que já tinha).

**Não feito ainda**: nenhuma automação de teste (esse projeto nunca teve suíte automatizada, só verificação manual ao vivo, prática já estabelecida); comparação de preço por unidade entre meses (ex: "R$/kg do arroz subiu") fica pro usuário calcular olhando o histórico filtrado — não construído como um gráfico dedicado, já que a métrica principal do dashboard é R$ total, não preço unitário.

## Problemas conhecidos

**"Erro interno do servidor" em qualquer rota que toca o banco (register/login/transactions)**: o módulo nativo `better-sqlite3` foi compilado para a versão do Node instalada quando `npm install` rodou (junho/2026) — se o Node da máquina for atualizado depois disso, o binário fica com `NODE_MODULE_VERSION` incompatível e todo `require('better-sqlite3')` falha (`ERR_DLOPEN_FAILED`). A rota engole o erro num `catch` genérico sem logar nada, então o único sintoma visível é o 500 no frontend. Corrigido em 2026-08-15 rodando:

```bash
cd backend && npm rebuild better-sqlite3
```

Depois é preciso reiniciar o servidor do backend (o processo antigo mantém o módulo quebrado carregado em memória). Se o erro voltar após uma atualização do Node, repetir esse rebuild — não é um bug de código, é um artefato de build desatualizado (`node_modules` é gitignored, então isso nunca fica "resolvido" permanentemente no repo).

**`npm run lint` falha com 4 erros `react-hooks/set-state-in-effect`** (achado em 2026-08-21, ao adicionar a aba Mercado): `dashboard/page.tsx`, `mercado/page.tsx`, `lib/auth-context.tsx`, `lib/i18n-context.tsx` — todos chamam uma função que faz `setState` dentro de um `useEffect` (o padrão `useEffect(() => { loadData(); }, [loadData])` usado pra carregar dados na montagem). `mercado/page.tsx` só repete o padrão já usado (e já quebrado) em `dashboard/page.tsx` desde antes — não é regressão introduzida pela aba Mercado, é uma regra de lint que o projeto nunca satisfez nesses 4 lugares. Não corrigido ainda porque mudar esse padrão é uma decisão de arquitetura mais ampla (afeta toda tela que carrega dados assim), fora do escopo do que foi pedido.
