## Visão do produto

App de controle financeiro pessoal focado em **compras de mercado**. A ideia central do usuário:

- A pessoa vai ao mercado e, conforme coloca itens no carrinho, registra cada produto e seu preço — digitando manualmente **ou** tirando uma foto (do carrinho/nota fiscal) para o app extrair os itens automaticamente via IA.
- Com isso, o app sabe não só "quanto gastei no mercado", mas **quanto cada produto individual custou**, mês a mês.
- Dashboards interativos devem mostrar: quanto a pessoa gastou a mais/a menos em relação aos meses anteriores, e **quais produtos aumentaram de preço** ao longo do tempo.
- Ou seja, o diferencial real não é só "livro-caixa" (entradas x saídas), é rastreamento de **preço por produto ao longo do tempo**.

## Estado atual do código (MVP já implementado)

Monorepo simples, dois apps Next.js separados, sem workspace compartilhado:

```
Controle Financeiro/
├── backend/    → API Next.js (porta 3001) — rotas em app/api/
└── frontend/   → Next.js + React + Tailwind v4 (porta 3000)
```

**Backend** (`backend/`):
- `lib/db.ts` — SQLite via `better-sqlite3` (`data/finance.db`), duas tabelas: `users` (id, name, email, password_hash) e `transactions` (id, user_id, type: 'income'|'expense', amount, description, date).
- `lib/auth.ts` — JWT (`jsonwebtoken` + `bcryptjs`).
- `lib/cors.ts` — helper de CORS/response JSON compartilhado entre rotas.
- Rotas: `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`, `GET/POST/DELETE /api/transactions` (com `summary`: totalIncome, totalExpense, balance calculados no GET).

**Frontend** (`frontend/`):
- `lib/api.ts` — client HTTP para o backend; `lib/auth-context.tsx` — contexto de auth (token em localStorage).
- Páginas: `/`, `/login`, `/register`, `/dashboard` (protegida via `ProtectedRoute`).
- Componentes do dashboard: `BalanceCard` (saldo), `ClusteredChart` (gráfico de colunas entradas x saídas por mês), `TransactionForm` (form manual: tipo/valor/descrição/data), `TransactionList`.
- Visual: tema dark com botões 3D neon (verde para entrada, vermelho para saída) — já com identidade visual definida, não é genérico.

**O que existe hoje é só um "livro-caixa"**: transação genérica com `description` livre, sem conceito de produto/item, sem mercado/loja, sem histórico de preço por item, sem OCR/câmera, sem app mobile (só web responsivo via Next.js).

**Categorias com cores neon (2026-08-17)**: transações ganharam um campo `category` (7 categorias fixas: Salário, Mercado, Moradia, Transporte, Lazer, Saúde, Outros), cada uma com uma cor neon própria definida em `frontend/lib/categories.ts` (espelhado em `backend/lib/categories.ts` para validação). Migração leve em `db.ts` (`ALTER TABLE ... ADD COLUMN category DEFAULT 'Outros'` se a coluna não existir) — transações antigas viraram automaticamente "Outros". `TransactionForm` ganhou um `<select>` de categoria; `TransactionList` mostra uma badge colorida por categoria. O gráfico original (`ClusteredChart`, Entradas x Saídas) saiu do verde/vermelho pra azul claro/vermelho neon; um novo `CategoryChart` mostra gasto por categoria por mês — só renderiza `<Bar>` para categorias efetivamente usadas nos dados, então o número de cores no gráfico cresce organicamente conforme o usuário varia as categorias (era o pedido original: "não ficar só nesse gráfico vermelho e verde").

## Região / moeda — 16 países (2026-08-18)

O app deixou de ser só sobre "controle de compra de mercado" pra ser **controle financeiro + conversor de câmbio**, com foco em quem viaja entre países da América Latina:

- `frontend/lib/regions.ts` — 16 regiões (Brasil, EUA + Argentina, Paraguai, Uruguai, Chile, Venezuela, Colômbia, Peru, Bolívia, Equador, El Salvador, México, Porto Rico, Honduras, Guatemala), cada uma com moeda, locale ICU (formatação numérica correta por país) e idioma (PT pro Brasil, EN pros EUA, ES pros outros 14 — Equador/El Salvador/Porto Rico usam Dólar de verdade, dolarização real, não erro).
- `backend/app/api/exchange-rates` + `frontend/lib/exchangeRates.ts` — cotação de câmbio **ao vivo**, buscada de uma API gratuita (open.er-api.com, sem chave), com cache de 12h (backend em memória, frontend em localStorage). Se a API cair, cai pra uma tabela fixa em `regions.ts` (`REGION_EXCHANGE_FROM_BRL`) como último recurso.
- `frontend/components/CurrencyConverter.tsx` — conversor independente (De/Para, qualquer um dos 16 países), pensado especificamente pro caso de uso "casal viajando de motorhome pela fronteira" que o usuário descreveu.
- `frontend/components/LanguageSwitcher.tsx` / `RegionSelect.tsx` — seletor de país/moeda (dropdown customizado com bandeiras em SVG próprio — `FlagIcon.tsx` — não emoji, porque o Windows não renderiza emoji de bandeira como imagem, só mostra o código do país em texto).

## Hospedagem real do backend (Railway) — 2026-08-21

Motivada por uma pergunta direta do usuário: por que o app parava de funcionar no celular sempre que ele fechava o notebook? Resposta honesta — o backend era só um `next dev` local, e o túnel usado pra testar no celular (ver Etapa 6) também rodava na mesma máquina; os dois morriam junto com o notebook. A solução real não é a Etapa 7 (publicação nas lojas, que trava em conta paga) — é hospedar o backend em algo que fique de pé sozinho, o que não precisa de conta paga nenhuma.

Configurado no Railway (mesma conta/serviço já usado pelo projeto irmão TechSpeak), pelo painel web, não CLI — a instalação do `@railway/cli` via npm falhou hoje (erro de resolução de versão) e o script oficial de instalação (`railway.app/install.ps1`) redirecionou pra uma página 404, então ficou mais rápido configurar direto pelo dashboard:

- **Root Directory**: `/backend` (o repo tem `frontend`, `backend` e `mobile` juntos; sem isso o build falha tentando entender as 3 pastas juntas).
- **Branch**: `feature/mvp-controle-financeiro`, não `main` — a `main` está dezenas de commits atrás (nunca recebeu nada das Etapas 1-6 do mobile). Decisão consciente de não mergear pra `main` só pra isso; é um passo separado.
- **Variáveis**: `JWT_SECRET` (novo valor gerado só pra produção, diferente do de desenvolvimento) e `FRONTEND_URL`.
- **Volume persistente** montado em `/app/data` — o banco é um arquivo SQLite (`better-sqlite3`) via caminho relativo (`process.cwd() + "/data/finance.db"`); sem volume, cada novo deploy apagaria todas as transações reais do usuário.
- **`backend/package.json`**: o script `start` tinha a porta fixa em `next start -p 3001` — corrigido pra `next start -p ${PORT:-3001}`, já que o Railway atribui a porta dele dinamicamente via `$PORT` (com `-p 3001` fixo, o servidor subia mas o proxy do Railway nunca achava ele).

URL real: `https://controle-financeiro-production-da55.up.railway.app`. Auto-deploy already ativado por padrão (todo push na branch conectada reimplanta sozinho). `mobile/eas.json` (todos os 3 perfis, incluindo `production` que antes não tinha nenhum `EXPO_PUBLIC_API_URL` e cairia no fallback `localhost`) e `mobile/.env.example` atualizados pra essa URL definitiva.

**Bug real achado logo no primeiro redeploy**: depois do primeiro push, o backend voltou 502 ("Application failed to respond") mesmo com o deploy marcado como bem-sucedido. Causa: o domínio público estava configurado manualmente pra rotear pra porta **3001** (herdado de quando a porta ainda estava fixa no código), mas o `next start -p ${PORT:-3001}` corrigido fez o servidor subir na porta **8080** de verdade — a porta que o Railway atribuiu dessa vez (visível no log: `Local: http://localhost:8080`). Corrigido direto no painel (Settings → Networking → editar a porta do domínio), escolhendo a opção "8080 (next-server)" detectada automaticamente pelo Railway em vez de digitar um número fixo — assim não quebra de novo se o Railway atribuir uma porta diferente numa próxima vez.

Verificado de ponta a ponta, de verdade: depois do fix de porta, `POST /api/auth/login` responde 400 corretamente contra a URL de produção; o usuário se cadastrou com a conta real (`andersunrise1@gmail.com`) direto pelo app já instalado no celular, sem o notebook precisar estar ligado durante o teste, e confirmou funcionando. **Persistência do volume também confirmada**: dois commits documentais seguintes dispararam redeploys reais (auto-deploy ativo), e depois deles o login com a conta real continuou funcionando normalmente — os dados sobreviveram aos deploys, não só a lógica parecia certa.

## Aba Mercado — registro rápido de compras (2026-08-21, web)

Pedida pelo usuário como uma forma de rastrear frequência de compra por produto ("estou comprando café toda semana?", "faz meses que não compro arroz") pra controlar excessos — separada do fluxo genérico de Nova Transação. Deliberadamente **não** é uma tabela nova: cada compra registrada é uma `transaction` real (`type: 'expense'`, `category: 'Mercado'`, `description: <nome do produto>`, `amount: <preço>`), reaproveitando 100% do schema/API que já existia — o gasto sai do saldo geral exatamente como qualquer Saída, mesmo que o usuário nunca tenha registrado uma única Entrada (confirmado ao vivo: saldo foi de R$0 pra -R$28,50 só com compras do Mercado, numa conta sem nenhuma Entrada).

`MercadoQuickAdd.tsx` — um botão só (não o par Entrada/Saída do formulário genérico), com rótulo dinâmico: "O que vamos comprar?" na primeira compra do mês corrente, "Qual próxima compra?" nas seguintes (checa se já existe alguma transação `category: 'Mercado'` com `date` no mês atual). Clicar expande dois campos (produto, preço); a data é sempre "agora", capturada automaticamente — não é um campo editável como no formulário genérico. `MercadoChart.tsx` agrupa as transações da categoria Mercado por nome de produto (normalizado por `trim().toLowerCase()` pra "Leite"/"leite" contarem como o mesmo item, mas exibindo a grafia como o usuário digitou), mostrando os 10 produtos mais frequentes num gráfico de barras — a mesma pergunta do usuário ("quais produtos comprei mais/menos") respondida por uma única lista ordenada. Nova página `/mercado` reaproveita o `TransactionList` existente (ganhou `titleKey`/`emptyKey` opcionais) filtrado pra só a categoria Mercado, em vez de duplicar a lógica de exclusão/busca/formatação que já existia. Link "Mercado" adicionado à `Navbar`; textos traduzidos nos três idiomas (`lib/i18n.ts`).

**Bug real achado durante a verificação, não do meu código**: as barras do `MercadoChart` (e, JÁ EXISTENTE antes dessa mudança, também as do `YearlyChart`) não desenham nenhuma forma visível nesse ambiente de teste automatizado — os dados chegam certos no componente (confirmado via `console.log` temporário), o Recharts cria os contêineres de cada barra (`.recharts-bar-rectangle`), mas o miolo (`.recharts-inactive-bar`) fica vazio, sem `<path>`/`<rect>`. Testado e descartado: não é versão do Recharts (reproduzido tanto na 3.8.1 quanto na 3.10.1, revertido pra 3.8.1 no fim já que atualizar não mudou nada), não é cache do Turbopack (reproduzido com `.next` limpo e servidor reiniciado do zero), não é HMR corrompido (reproduzido numa aba nova, sem histórico de erro no console). Causa mais provável: esse ambiente de automação de browser não composita frames de verdade quando o painel não está visível (o mesmo motivo pelo qual `screenshot` falha aqui com "pane is not displayed") — o Recharts parece depender de um `ResizeObserver`/layout real pra desenhar a forma da barra, e isso nunca dispara sem compositing genuíno. **Não afeta a funcionalidade real** (dados, cálculo de saldo, histórico, tudo verificado correto) — só não deu pra confirmar visualmente que as barras aparecem numa tela de verdade. Vale conferir num navegador real (não essa ferramenta) na próxima vez que alguém abrir o Dashboard ou o Mercado.

**Portado pro mobile no mesmo dia (2026-08-22)**: `MercadoQuickAdd.jsx`, `MercadoChart.jsx` e `MercadoScreen.jsx` espelham os componentes web 1:1, mesmos textos/comportamento. **Bug real achado e corrigido durante a verificação, específico do mobile**: depois de registrar uma compra no Mercado e trocar pra aba Dashboard (sem recarregar a página), o saldo continuava mostrando o valor antigo — as abas do React Navigation ficam montadas em segundo plano ao trocar de aba (diferente de navegação por rota no Next.js, que sempre remonta), então o `useEffect(() => { loadData() }, [loadData])` de cada tela só rodava uma vez, na primeira montagem. `DashboardScreen.jsx` e `MercadoScreen.jsx` trocaram esse `useEffect` por `useFocusEffect` (`@react-navigation/native`) pra recarregar toda vez que a aba ganha foco, não só na primeira vez — confirmado ao vivo: registrei uma compra no Mercado, troquei pra Dashboard sem reload nenhum, e o saldo já veio certo (-R$32,40, duas compras). `AdminScreen.jsx`/`FeedbackScreen.jsx` não foram tocados — não têm esse mesmo problema de dados compartilhados entre abas.

## Problemas conhecidos

**"Erro interno do servidor" em qualquer rota que toca o banco (register/login/transactions)**: o módulo nativo `better-sqlite3` foi compilado para a versão do Node instalada quando `npm install` rodou (junho/2026) — se o Node da máquina for atualizado depois disso, o binário fica com `NODE_MODULE_VERSION` incompatível e todo `require('better-sqlite3')` falha (`ERR_DLOPEN_FAILED`). A rota engole o erro num `catch` genérico sem logar nada, então o único sintoma visível é o 500 no frontend. Corrigido em 2026-08-15 rodando:

```bash
cd backend && npm rebuild better-sqlite3
```

Depois é preciso reiniciar o servidor do backend (o processo antigo mantém o módulo quebrado carregado em memória). Se o erro voltar após uma atualização do Node, repetir esse rebuild — não é um bug de código, é um artefato de build desatualizado (`node_modules` é gitignored, então isso nunca fica "resolvido" permanentemente no repo).

**`npm run lint` falha com 4 erros `react-hooks/set-state-in-effect`** (achado em 2026-08-21, ao adicionar a aba Mercado): `dashboard/page.tsx`, `mercado/page.tsx`, `lib/auth-context.tsx`, `lib/i18n-context.tsx` — todos chamam uma função que faz `setState` dentro de um `useEffect` (o padrão `useEffect(() => { loadData(); }, [loadData])` usado pra carregar dados na montagem). `mercado/page.tsx` só repete o padrão já usado (e já quebrado) em `dashboard/page.tsx` desde antes — não é regressão introduzida pela aba Mercado, é uma regra de lint que o projeto nunca satisfez nesses 4 lugares. Não corrigido ainda porque mudar esse padrão é uma decisão de arquitetura mais ampla (afeta toda tela que carrega dados assim), fora do escopo do que foi pedido.
